# Control-plane ownership

Astra owns project identity, conversations, run admission, settings, secrets, approvals, artifacts, audit records and the user interface. Backends do not determine Astra's product architecture.

```text
React workspace → authenticated local REST API → Engine
                                             ├─ SQLite event / entity store
                                             ├─ passphrase-encrypted provider vault
                                             ├─ Responses / compatible adapter
                                             │  ├─ artifact tool
                                             │  ├─ isolated browser tools
                                             │  └─ remote MCP approval responses
                                             └─ Codex JSON-RPC adapter → pinned app-server
```

## Modules

- `server/index.mjs`: authentication, input validation, provider probing, API routes and loopback hosting.
- `server/store.mjs`: transactional SQLite storage with WAL. Entity kinds are explicit; primary IDs are generated by the server.
- `server/security.mjs`: vault, session lifetime, endpoint and primitive validators.
- `server/engine.mjs`: admission limits, lifecycle, approvals, events, artifact storage and restart reconciliation.
- `server/responses.mjs`: provider-specific request/response and tool continuation protocol.
- `server/codex.mjs`: version-bound app-server transport and protocol translation. No copied Codex agent implementation.
- `server/requests.mjs`: backend approval and question protocol translation, including explicit rejection of unknown interactions.
- `server/browser.mjs`: isolated browser context, destination checks and narrowly described tools.
- `src/App.jsx`: shell and composition; management and inspector behavior reside in separate modules.
- `sdk/client.mjs`: optional local programmatic client.

## Backend contract

Adapters receive a run snapshot, project and conversation, credential, AbortSignal, event emitter, usage recorder, message recorder, approval callback and allowed tool executor. They report actual outcomes and throw failures. The engine remains responsible for terminal state.

Additional backends must preserve these invariants:

1. Persist the run before execution starts.
2. Execute only the selected backend and model.
3. Record returned usage without inventing costs.
4. Never silently bypass a requested approval or a backend sandbox restriction.
5. Treat cancellation and transport loss as non-success.
6. Persist produced output and explicit continuation handles.
7. Do not expose provider secrets through public state or audit exports.
8. Do not replay pending side effects on restart.

## Run lifecycle

`queued → running ↔ awaiting_approval → completed | failed | cancelled`

A server restart reconciles nonterminal runs to `interrupted`. Pending approvals become `expired`. Continuation creates a new run in the existing conversation; Codex resumes its thread ID while Responses rebuilds explicit local conversation history.

## Limits

The server limits two concurrent runs globally and one per conversation. Context admission uses a conservative character estimate (three characters per configured token); provider token usage is authoritative for recorded consumption. It is not a model-specific tokenizer. Responses enforces a cumulative output cap across tool rounds; provider input may be billed again per request. Dollar estimates omit caching discounts and tool charges.

Approval records and events are append-oriented through the normal API but are not cryptographically tamper-evident against the local machine owner. The mutable entity schema is a pragmatic local baseline, not a multi-tenant audit ledger.

## Compatibility

Pinned Codex 0.107.0; regenerate its JSON schema and test the adapter before upgrading. Initialize and thread/start were verified against the actual installed executable. No live coding success is claimed until provider authentication and a writable sandbox are exercised. The current Windows probe returned readOnly.

No backend auto-detection chooses a paid provider. The owner connects a provider and selects a model. Responses is independent of Codex and can remain active if Codex is absent or unavailable.
