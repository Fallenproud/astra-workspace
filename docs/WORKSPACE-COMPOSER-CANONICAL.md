# Workspace Composer Canonical — Astra integration

The adjacent source document is the supplied product behavior contract, preserved verbatim. Its SOPHIE-X COMMAND / Daycostra naming describes the source ecosystem; the user requested its composer behavior for Astra, not a product rebrand. Astra's canonical identity and immutable authority controls remain unchanged.

The host registers five read-only primitives: Activity, Files, Context, Artifacts and Workflow. Task intent selects a minimal initial layout; selection is deterministic in development. Approved artifact production expands the layout. Every compose/adapt/template action is recorded in the run events. Existing approvals stay in the host inspector and remain subject to the Show controls.

Responses/compatible agents receive compose_workspace with an enumerated, validated schema and a required task-related reason. It cannot change navigation, branding, keys, capabilities, runtime status or approval gates. Unknown/privileged primitive requests fail. The Codex backend keeps its existing app-server protocol; host-side composition still applies.

Each conversation retains its current layout in SQLite. The user can hide views, inspect actual files/results, explicitly save a reusable layout and apply it to another task. Templates preserve purpose, structure, read capabilities, data contracts and runtime dependencies; they grant no execution privileges. Full application promotion is not automatic.

Terminal, arbitrary HTML/UI, external browser embeds, deployment controls and unsupported editors are not registered. A desired primitive is not a capability grant. Existing execution tools remain the only route to consequential work. No hidden reasoning is stored as evidence.
